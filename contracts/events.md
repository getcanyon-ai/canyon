# Seam 2 — the run timeline

**Persisted rows, read by polling. No push transport** (decided 2026-09-04, `canyonv2-kaq`).
The dashboard and the CLI render from these rows; the server writes them. The ledger is the
product: every row outlives any connection, replays from the store, and is what the audit
screens read. A client that slept re-polls — there is nothing to reattach to and nothing to
replay anonymously.

## Row

```jsonc
{ "id": 41,                          // monotonic within its scope — the paging cursor
  "ts": "2026-09-02T09:31:04Z",
  "scope": "run",                    // run | org
  "run": "gr_8f2a",                  // present when scope = run
  "project": "claims-portal",        // present in both scopes
  "kind": "check.completed",         // from the catalogue below, nothing else
  "data": { }                        // kind-specific, shapes below
}
```

## Run scope — `GET /api/v1/gate-runs/:id/timeline?after=<id>&limit=<n>`

Returns `{rows: [Row], next: <id> | null}` — rows ordered by `id` ascending; `after` is an
exclusive cursor (omit for the start); `limit` defaults to 100, max 200; `next` is the last
`id` returned, `null` when the run has ended and nothing follows. Clients poll about once a
second while a run is `pending` or `running`; `GET /gate-runs/:id` remains the state read.

## Org scope — `GET /api/v1/timeline?after=<id>&limit=<n>`

Same envelope and paging. The fleet page polls this instead of N run timelines.

| kind | data | notes |
|---|---|---|
| `app.updated` | `{project, row}` | fleet row upsert — the live row at minute 13 · a member is answered it only for the apps they are `contributor` or above on (routes.md, *App teams*) |
| `tiles.updated` | `{tiles: {secrets_exposed, blocked, approved, never_reviewed, unowned, failed, refused}}` | absolute values, not deltas — the minute-9 decrement · the seven counters `GET /api/v1/fleet` serves (routes.md row 75), defined there: one tile vocabulary, not two · **the counts the reader's own fleet read answers** — org-wide for an admin, the reader's team apps for everyone else — never the whole fleet's to a member. A stacks tile waits for stack detection |
| `run.transition` | `{project, run, state, kind?}` | per-row activity on the fleet page · `kind` `patch` on a patch run's row (routes.md, *Patch runs*; amended 2026-10-18, #2086), absent on any other, so a change bridge polling this stream tells Canyon's patches from people's runs · a member is answered it only for the apps they are `contributor` or above on |
| `audit.appended` | `{event_id}` | audit screens poll this · a member is answered only the ids of events the audit read answers them (routes.md, the audit read) |

Rules:

- Both list routes run the request pipeline like any other `/api/v1` route — the session stage,
  so there is no anonymous read of history; no audit row, they are reads (routes.md row 75) —
  except `GET /api/v1/projects/:id/logs`, the one read that can disclose a secret value, which
  writes one row naming the reader and the environment and nothing from the stream (row 119).
- Rows are append-only; a row is never edited or deleted (retention is by run, per the
  package retention window, and is itself an audit event).
- A row is stored once and projected for its reader at read time: `app.updated`'s row as that
  reader's fleet read would answer it (requests to owners and admins only), `tiles.updated` their
  counts, and rows of apps below their level left out.
- An unknown `kind` in a row ⇒ the reader **ignores the row and surfaces it**; it never blocks
  rendering of the rest.

**Recorded fixture** (added with the CI check): one complete claims-portal gate run — queued →
checks → `producer.sarif` rows → blocked verdict → (fix) → second run → clean → deploy — as a
JSON array of rows, replayed by dashboard and CLI tests instead of a live server. The CI check
validates every row against this schema and every `verdict.findings` / `producer.sarif`
payload against seam 1. This fixture is what lets Track B start on day 1.

**Golden fixture:** the recorded claims-portal run — the blocked gate at minute 9, the fix, the
clean gate and the preview deploy, in both scopes — is derived from the seam-1 golden log by
`contracts/testdata/timeline/generate.py` so the two cannot drift. `contracts/validate.py`
imports it and checks every row against `contracts/schema/timeline-row.schema.json` and the
invariants above: ids strictly increasing and timestamps monotonic within each scope, kinds from
their scope's table and every kind exercised, each run pending → running → one terminal state,
embedded `producer.sarif` and `verdict` logs pass the seam-1 checks and belong to their producer,
verdict counts match their findings, the first verdict is the golden log, and the story runs
blocked → clean → deploy of the clean run. The
JSON is not committed (over a thousand lines, rule 3); running the script writes it next to
itself.
