**Canonical for the experience — what the visitor sees, reads, and does.** `ARCHITECTURE.md`
owns mechanism and wins on how the system works. The detail specs in `design/specs/` (CLI
transcripts, screen copy, launch assets) carry the full texts; where one conflicts with this

## D1 — Severity model

- Findings carry a **severity**: `critical · high · medium · low`. Four steps, no "info" tier.
- **Blocking is derived, not a severity**: a finding blocks the gate it is judged in (D14) iff **its policy is set to Blocking AND severity is critical or high** (or the review flagged it as a security issue, which is treated as high).
- UI chips, CLI output, and README show the severity word. Verdict lines count blocking findings: `✗ Blocked — 1 blocking finding`.
- `--format ai` carries `severity:` AND an explicit `blocks: yes|no` per finding. Agent instructions and the skill key off `blocks`, never off severity vocabulary — skill text reads *"For each finding with `blocks: yes`…"*.
- Example: the xlsx CVE is severity high, but the `deps.known-vuln` policy ships in **Advisory**, so it warns, not blocks. An advisory finding that stays advisory is the point — the gate isn't hunting for excuses to block.

## D3 — Ports and URLs

- Dashboard: `http://localhost:7777`, **bound to 127.0.0.1** (compose fails loudly with the fix if the port is taken).
- Previews/prod are **host-routed, one rule everywhere** (decided 2026-09-11): `http://<app>.preview.localhost:7777` and `http://<app>.prod.localhost:7777` on the demo host; on Kubernetes `https://<app>.<env>.<domain>` or `https://<app>-<env>.<domain>`, the admin's choice of form, `domain` Canyon's own host unless the admin names another (decided 2026-09-26, contracts/routes.md `/api/v1/front-door`). One image serves every environment, no path prefix compiled into the app. Chrome and Firefox resolve `*.localhost` to the machine; the macOS system resolver and Safari do not, so the README gives the one-line alternative (a hosts entry, or a public wildcard name pointing at the machine) — the server routes on the Host's first two labels whichever the engineer uses.
- Domain `getcanyon.ai` (the docs at `https://www.getcanyon.ai/docs/`), GitHub org `getcanyon-ai`: the source at `getcanyon-ai/canyon`, downloads at `getcanyon-ai/canyon-releases` (decided 2026-11-04, #2661).

1. `secrets.client-bundle` · critical — Stripe live key at `apps/web/src/lib/payments.ts:14`, **gitleaks'** `stripe-access-token` (decided 2026-10-01: OSS tools only). The card's title is gitleaks' own (`Found a Stripe Access Token, posing a risk to payment processing services and sensitive financial data`), its line hidden whole, and the fix is the policy table's: rotate the key, then delete it from the code if nothing reads it, or `canyon secret set STRIPE_ACCESS_TOKEN` and read it from the environment. commission-calc's `rk_live_` key in Vite code is the same rule.

## D6 — Verdict UX invariants

- The blocked promote button is **present, disabled, labeled with the thing you want**; explanation always visible, never a tooltip; the receipt lists what **passed** next to what didn't (gate, not wall).
- The override exists, is never silent: required free-text reason, "stays attributed to you," names who sees it.
- **The unlock animation** (receipt row flips → 160ms later the button fills) is the one carefully-built animation. Cause visibly precedes effect. No confetti anywhere in the product.
- Promote asks once before it sends (D5's confirm line) and, once the server takes it, answers `Promotion of <app> started. Production shows the new version here once it is live.` Promotion is a background run with live progress, so nothing says "promoted" before production is live: the run's lines follow under the button (and in `canyon deploy --env prod`) and end on `live at <url>` or on the reason it failed. No success modal, no confetti.
- Findings **dim during re-review, never disappear** before the result is known.
- Fail-closed everywhere: unparseable severity blocks; a missing review blocks; "never reviewed" ≠ "clean".
- Screens use the user's words: a version is its label, else its id without `pkg_`; the words package, receipt, stage and fingerprint never appear on a screen (the dashboard's tests assert it), and neither do grant and level — access reads `read-only`, `contributor` and `owner`.

## D7 — CLI + skill

- **Twenty-three commands** (`design/specs/cli.md` §1; `canyon mcp`, §6.15, added 2026-11-20: Canyon's tools over MCP for a coding agent, design/specs/mcp.md; `canyon demo`, §6.14, added 2026-11-13, #2862: it starts and stops the laptop demo, the one verb that runs Docker, and it decides nothing a host decides; `canyon demo tour`, §6.14.1, #2861, is the guided tour on that demo, whose words ship in the binary) — no `init`, no `fix`, no TUI, no inline suppressions. Exit codes `0/1/2/3`, `3` a deploy, promotion, rollback or check whose end this command doesn't know: still running in Canyon, or ended unread (#2721, #2730).
- **The CLI is a courier** (see `ARCHITECTURE.md`): it moves code, renders server-sent events, and hands agents the org's settings. All scanning, policy, review, build, deploy decisions are server-side.
- `check` ≡ `deploy` gate — **structurally true under the split**: both are one server-side gate run; `check` stops before build.
- **`canyon share`** says who can open an app (`design/specs/cli.md` §6.7; the model is `design/PERMISSIONS.md`). The skill adds three rules: write a one-line `description` in `canyon.toml` before the first deploy · after a deploy, tell the user who can open the link · never run `canyon share` unless the user asks to share or send someone a link; then share exactly who they name, read-only unless they say otherwise, `everyone` only when they say everyone.
- `--format auto` detection (harness env vars → `ai`); rendering is a client concern over server-sent structured findings.
- AI-format findings carry `required end state`, `suggested fix` ("Run exactly:"), and the **`do not:` block** naming the cheat moves; two-round loop cap naming the human override exit.
- `canyon secret set --from-gate` — the credential never transits the chat; 15-min validity; audited; rotation nudge. The skill carries **no window-ordering instruction**: adoption resolves to the most recent run with a live candidate, so ordering doesn't matter.
- **The skill ships with the binary** (`ARCHITECTURE.md` §4 is canonical): `canyon skill install` writes the shipped, `--print`-able skill per harness (marker-delimited, idempotent, auditable against the release); `canyon manifest` hands agents typed data, live at session start — host URL, active policy list, component menu — and, under each Canyon rule that blocks, one line on how to pass it, Canyon's own words, which the dashboard's *What agents are told* shows as well. The one exception to typed data is a custom rule's own text, as its admin wrote it, handed for a custom rule that blocks alone under `Your org's own rules (written by its admins):`: only admins write it, every version is audited, and it never holds a secret (amended 2026-11-03, #2622). Other org-authored sections are day 2, under §4's guardrails. Shipped default skill text: `design/specs/cli.md` §7.2, with severity language replaced by `blocks: yes`.

## D8 — Voice

The subject is the code, never the person. No "violation/non-compliant/failed". One sentence of why naming the real consequence. Pick a fix and say why. Say when something doesn't matter. Say what the fix doesn't cover ("rotate it"). No exclamation marks, no emoji in findings. The org owns the rule; Canyon enforces it.

## D9 — Promises cut or made honest

1. **Incident reachability** → v1 copy is "used directly in a request handler" vs "present in lockfile only". The `[ Open 3 patch PRs ]` button is CUT (needs write access to the org's VCS); replaced with `[ Copy the fix for your agent ]`.
2. **Bundle-byte confirmation** → CUT. The gate never builds; a key is gitleaks' finding wherever it sits in the code, which `check` and `deploy` can assert identically. "Nothing was built and nothing was deployed." stays literally true.
3. **`check` ≡ `deploy` guarantee** → KEPT, made honest by cutting everything that requires a build during review. Same package hash, same scanners, same model, same policy snapshot. The LLM verdict is cached by (package tree, policy snapshot, model, agent) and a completed review is replayed on re-check, so the AI review of the same package under the same policy and model can't flip; a skipped or failed review is retried, and attached reports are read afresh on every run.

## D10 — The model question

- **The sample apps' reviews are REAL runs**: the demo deploys them through Canyon on first boot, so their findings change if their source changes. The other seeded verdicts (commission-calc's key) are recorded rows in the shape a real run writes. The seeded `ai review` rows say `skipped`, as on any host with no model: nothing is pre-recorded, and the README says no model key is needed.
- **The model is HOST config**, set once by whoever runs the host on the server container, never per-laptop env: `CANYON_MODEL_PROVIDER` (`anthropic`, the default), `CANYON_MODEL` (the id as that provider names it — Canyon maps none), `CANYON_MODEL_URL` (a gateway or proxy that speaks the Anthropic Messages API, including one in front of Bedrock or Vertex, whose own SDKs this build does not carry), and exactly one credential: `ANTHROPIC_API_KEY`, or `CANYON_MODEL_TOKEN` where the gateway holds the provider key and this host holds none. The rule is that naming any of them asks for a model and the boot fails with the reason unless a credential resolves — naming none is the only way to have no model. Without one, the row renders `ai review · skipped (no model configured on this Canyon host)` — visibly skipped, never silently passing.
- **"What leaves your machine":** your code goes to *your* Canyon host — in the demo, that's localhost; in a company deployment, the host the platform team runs. The host calls a model only if its admin configured one.

## D14 — The gate pipeline (decided 2026-10-02, the redesign #1401)

Decided with the redesign. It is built after the scanner rebuild (#1315) and custom rules (#1316),
which change the checks themselves; until then the code's current behaviour is the gap, not the
rule.

- **Two gates, in order.** Every version passes **Before preview**, then **Before production**.
  - *Before preview* is the review every `check` and `deploy` runs (D7: `check` ≡ `deploy` holds for it). A Blocking check there keeps the version out of preview: nothing is built and nothing is deployed.
  - *Before production* is judged when a person clicks Promote. A Blocking check there keeps the button disabled, and the receipt says why (D6).
  - Their lines: `Before preview` — `Runs on every check and deploy. A Blocking check keeps the version out of preview.` · `Before production` — `Checked when a person clicks Promote. A Blocking check keeps the button disabled.`
- **A check is one rule of D2, with a state per gate.**
  - In each gate a rule is `Off`, `Advisory` or `Blocking`; a rule not placed in a gate is Off there. A rule can sit in both gates with a different state in each: `deps.known-vuln` Advisory before preview and Blocking before production.
  - #1315 decides which rules each scanner card on the screen holds.
  - The go-live rules (`prod.clean-gate`, `prod.human-approval`, `owner.required`, `stack.blessed`, `platform.known-vuln`, `prod.egress-allowed`) sit only before production, and stay editable like any rule, Off included (routes.md, the policies row: the owner, 2026-09-22).
- **The review runs every rule that is not Off in either gate**, so the findings Before production judges always exist.
  - Before production re-reads them and never re-scans. It derives `blocks` against the org's state at the moment of reading, as the receipt does; the stored verdict keeps the `blocks` it was derived with for Before preview.
  - Promote still ships exactly the image preview runs (D5), and the promotion stays bound to the run it was judged on (D12).
- **`blocks` answers the run's gate.**
  - On `check` and `deploy`, a finding's `blocks` is Before preview's.
  - What keeps a version from production is the promote receipt, which lists every rule placed before production.
  - An approval covers its finding in both gates.
- **The org's rules are the admin's; an app's additions only tighten.**
  - Admins place, move and set the org's rules on Guardrails › Pipeline.
  - An app owner may add to their own app: a rule this host has that the org does not run, or an org rule raised in a gate. Writing a custom rule stays an admin's.
  - An addition never removes or weakens an org rule: for every rule in every gate, the state in force is the stricter of the org's and the app's (Off < Advisory < Blocking).
  - An app's additions are part of its runs' snapshot, and so of the verdict cache's key (ARCHITECTURE.md).
  - Admins see every app's additions on the Pipeline tab; a member sees those of the apps they are contributor or above on (`design/PERMISSIONS.md`).
- **Fail closed (D6).**
  - A rule whose state in a gate cannot be read counts as Blocking there.
  - A gate that cannot be read keeps the version where it is, and says it could not be read; it never reads as passed.
- **A change is previewed and saved like a policy** (screens.md A4b): it says what it would keep from production today, collects in the tab's one save bar, and a tightening may wait a grace (D2). The pipeline gates promotion, never a running app.
- **The app page draws the same two gates** with each version on them.

## D15 — What needs a person (decided 2026-11-08, #2724)

Decided after the owner found an app whose calls out Canyon refused reading `Passed · 3 warnings` in the fleet and
`v5.0 is live in production` on its page, with the only Allow at the bottom of the page. The wire is
`contracts/routes.md`, *What needs a person*; the screens follow it in the next two PRs.

- **A decision waiting on a person outranks a good status.** Green never shows for an environment while something on it
  waits for a person.
- **One list, computed once, by the server.** The fleet row, *Needs you*, the side pane, the app page's band, the
  go-live box and the rail's count read the same `needs[]`, in the same order. No screen works out its own, and none
  parses another's words. The receipt's two kinds, a finding that blocks production alone and what production will
  refuse, ride the status read alone, which evaluates the receipt: the fleet never does.
- **What Canyon couldn't check is never all clear.** An environment whose running state a read couldn't tell is no need of its
  own, which would flood the list while the executor is down, but the screens say how many they couldn't check, and never
  say nothing needs a person while there are any (decided 2026-11-09).
- **The order** is the people using the app first: production held, production down, a call production refuses, a
  secret in the code, a production approval asked, a version blocked or not checked, then preview's, a patch waiting,
  a request for access, no owner or never reviewed, and an app on its old network (routes.md has the ranks).
- **Every need says what the app can't do, then who decides, and the fix where the sentence is.** A reader who can't
  act sees who can: the admins by name where the need is theirs to hand on, the owners by name otherwise.
- **Never more than the reader's level reads** (design/PERMISSIONS.md). A read-only member learns nothing of what the
  team sees, as a held production already reads to them as nothing deployed; the app's page names who looks after it.
  A responder with no grant sees a hold to lift and nothing else. A request for access is its owners' and admins'.
- **The owner's decisions (2026-11-08):** who can open an app moves up under its name, and a request for access is a
  need; every need names who can fix it. Allow and Dismiss work from the fleet's *Needs you*, with Undo, to whoever may
  use the Outbound card's, audited as there. A message to Slack or Teams is its own work (#2725). `prod.egress-allowed`
  stays Off by default.
- **Decided 2026-11-08:** a refused call is red in production and amber in preview;
  the rail's count is the lines the reader sees, each kind shown only at its level; an admin's list covers the org,
  five lines then `Show <n> more`, and *Your apps* narrows it; responders see no blocked version unasked, the author
  hands it on with a link; a need about outbound carries no Beta chip (D5's Beta row).
